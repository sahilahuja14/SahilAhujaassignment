# REVIEW.md

This review records the defects I found in the starter `app/main.py`, how each problem could be reproduced, and how the implementation now addresses it. The fixes are intentionally tied to the OpenAPI contract and `DATA_MODEL.md`, so each reason can be checked against a rule, endpoint response, or MongoDB query plan.

| # | Where | What was wrong | How to verify the defect | How it was fixed |
|---|---|---|---|---|
| 1 | MongoDB client setup | The starter used the default PyMongo datetime behavior, which can return naive datetimes. It also had no short server selection timeout, so a dead MongoDB server could delay readiness checks. | Start the app without MongoDB available and call `/health`; the old version did not fail quickly or clearly. | The client is configured with UTC-aware datetimes and a short server selection timeout. API serialization always converts stored datetimes to epoch milliseconds. |
| 2 | Application startup | The starter did not create any indexes. This left uniqueness, race safety, list performance, analytics performance, and explain-plan requirements unsupported. | Inspect `db.employees.list_indexes()` and `db.attendance_logs.list_indexes()` after startup; only `_id` existed in the seeded database. | Startup now creates unique identity indexes and compound indexes for attendance listing, punch-out lookup, analytics, and department queries. |
| 3 | `GET /health` | The health endpoint returned `{"status": "ok"}` without checking MongoDB. That could make the grader start tests before the database was actually reachable. | Point `MONGO_URI` to an unavailable server and call `/health`; the starter still reported success. | `/health` now runs `db.command("ping")` and returns HTTP 503 if MongoDB cannot answer. |
| 4 | `compute_late_minutes` | The helper used the punch-in datetime's own date and timezone instead of the IST attendance date required by R1. Overnight shifts were therefore calculated against the wrong shift day. | Use an overnight employee with shift `22:00` to `06:00` and punch in before 06:00 IST; the starter assigns the wrong attendance day. | The code now computes the attendance date in IST first, then builds shift start and end instants from that date. |
| 5 | `compute_late_minutes` | The strict grace rule was incomplete. R2 says 09:40:00 is not late for a 09:30 shift, but 09:40:01 is late by 10 whole minutes. | Test punch-in times around the grace boundary: `09:40:00`, `09:40:00.900`, and `09:40:01` IST. | Instants are truncated to whole seconds before calculation, and lateness is applied only when the elapsed seconds are strictly greater than 600. |
| 6 | `compute_work_hours` | Python's built-in `round` uses banker's rounding, while R4 requires half-up rounding. | Construct a duration whose second-to-hour conversion lands exactly on a half value at two decimals. | Work hours are calculated with `Decimal` and `ROUND_HALF_UP`. |
| 7 | `compute_overtime` | The starter counted any positive overtime, but R3 only counts overtime when it is at least 30 whole minutes. It also did not handle overnight shift ends. | A shift ending at 18:30 with punch-out at 18:35 should return 0, not 5. An overnight shift should end on the next calendar day. | Overtime now uses the correct shift-end instant and returns minutes only when the delta is at least 30 minutes. |
| 8 | Request models | The starter accepted invalid employee fields, invalid shift times, invalid emails, equal shift start/end, and malformed dates. | Send a create-employee request with an invalid email, `joined_on`, or identical shift times. The old code accepted values that should be HTTP 422. | Pydantic constraints and validators now enforce the contract at the request boundary. |
| 9 | `POST /employees` | Duplicate employee creation used a check-then-insert pattern. Under concurrency, two requests could both pass the check before either insert completed. | Send two parallel requests with the same `emp_code`. The old code depended on timing. | The endpoint inserts directly under a unique `emp_code` index and maps `DuplicateKeyError` to HTTP 409. |
| 10 | `POST /employees` | The starter returned raw Python datetimes and used local naive `datetime.now()`. The API contract requires epoch milliseconds. | Create an employee and inspect `created_at`; it should be an integer epoch millisecond value, not an ISO string or raw datetime. | The implementation stores UTC datetimes and serializes `created_at` as epoch milliseconds. |
| 11 | `GET /employees` | Pagination skipped `page` multiplied by `page_size`, which skips the entire first page. | Call `/employees?page=1&page_size=20`; the old code started from the second page. | Pagination now skips `(page - 1)` multiplied by `page_size`. |
| 12 | `GET /employees` | `total` ignored the department filter, and results were not sorted by `emp_code`. | Call `/employees?department=Sales`; the old `total` could describe all employees instead of the filtered set. | The endpoint counts the filtered query and sorts by `emp_code` ascending. |
| 13 | `POST /attendance/punch-in` | Unknown employees were not handled before shift fields were accessed. This could cause a server error instead of the required 404. | Punch in with an employee code that does not exist. | The endpoint now checks the employee first and returns HTTP 404 when missing. |
| 14 | `POST /attendance/punch-in` | The starter accepted unsupported statuses and loose timestamp values. The contract rejects `ABSENT`, `LEAVE`, strings, floats, explicit nulls, and seconds-looking values. | Send `status=ABSENT`, `punched_at=123`, or `punched_at=null`. | Strict request models now accept only presence statuses and valid integer epoch milliseconds. |
| 15 | `POST /attendance/punch-in` | The attendance date was taken from the local server date, not from the IST business rule. Overnight shifts were especially wrong. | Use a punch-in before the overnight shift end, such as before 06:00 IST. | The endpoint now applies R1: convert to IST, handle overnight shift assignment, truncate to whole seconds, and store the corrected UTC instant. |
| 16 | `POST /attendance/punch-in` | Attendance uniqueness also used check-then-insert. Two parallel punch-ins for the same employee and date could both attempt to create a record. | Send simultaneous punch-ins for the same employee and instant. | The endpoint relies on the unique `(emp_code, date)` index and converts duplicate insert errors to HTTP 409. |
| 17 | Attendance responses | The starter exposed an `id` derived from MongoDB `_id`, but the contract says `_id` is internal and attendance records are addressed by `(emp_code, date)`. | Compare the response body with the OpenAPI `AttendanceRecord` schema. | Serializers now remove MongoDB internals and return only contract fields. |
| 18 | `GET /attendance` | The starter loaded all matching documents, sorted them in Python, and then paginated. That is not acceptable for the 100,000-record requirement. | Populate a larger collection and observe memory use and latency, or inspect the code path. | Filtering, sorting, skipping, and limiting are now pushed into MongoDB with matching indexes. |
| 19 | `GET /attendance` | The old endpoint sorted only by date and did not apply the required tie-breaker of `emp_code` ascending. | Insert two records on the same date and compare response order with the contract. | The endpoint now sorts by `date` descending and `emp_code` ascending. |
| 20 | Missing punch-out endpoint | The starter did not implement `/attendance/punch-out`, so work hours, overtime, and half-day values could not be written through the API. | Call `POST /attendance/punch-out`; the starter returned 404 because the route did not exist. | The endpoint now finds the latest open punch-in at or before the punch-out time, validates the 24-hour window, computes derived fields, and updates atomically. |
| 21 | Missing regularization endpoint | The starter did not implement manual corrections or audit history. | Call `PATCH /attendance/{emp_code}/{date}`; the starter had no route. | The endpoint now applies status and punch-time corrections, recomputes derived fields, appends one history entry, and rejects no-op corrections. |
| 22 | Missing analytics endpoints | Monthly employee summary, department summary, late leaderboard, and department trend were not implemented. | Call any `/analytics/...` endpoint in the starter. | The implementation adds MongoDB aggregation pipelines for each analytics endpoint and reads stored derived fields as required. |
| 23 | Missing explain endpoint | The starter did not provide `/admin/explain/{endpoint}`, which is required to prove index-backed query plans. | Call `/admin/explain/attendance_list`; the starter had no route. | The implementation builds explain output from the same query or pipeline builders used by the real endpoints, including index hints. |

Also checked: the default shift values of `09:30` and `18:30` match the OpenAPI schema, so I kept those defaults instead of changing them.
